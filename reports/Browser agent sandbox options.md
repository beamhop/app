# Layer the sandbox, broker every capability

Beamhop can give every member a real agent workspace with nothing installed, but not by picking one "Linux in the browser" engine. The option space splits into three tiers: browser primitives (sandboxed iframe, workers, WASM tools, a virtual shell), language runtimes in WASM (Pyodide, QuickJS), and full Node/Linux userlands (BrowserPod, WebContainers, emulators). Only the first two run on every device including iOS, and only one tier-three engine, BrowserPod, has been shown running unmodified Claude Code, Codex CLI and Pi in a tab; it is closed source, CDN-loaded, desktop-only and excluded on iOS. The recommended shape is therefore a small, open, universal sandbox that Beamhop owns (it already has the core of it), with a heavy desktop-only "full workspace" as an optional capability that one member can host and others can use through the room. On subscriptions, no provider offers a supported flow in which a hosted static page obtains subscription-backed inference: OpenRouter's PKCE flow and pasted API keys are the only paths that are browser-feasible, permitted and officially supported, OpenAI's "Sign in with ChatGPT" is the closest subscription route but is documented with a loopback callback, and the Gemini sign-in Beamhop ships today reuses a client Google has suspended accounts over. In a multi-user room the dominant risk is exfiltration by prompt injection through whatever the agent is allowed to reach, not sandbox escape, so the design has to be a capability broker in the trusted page with the sandbox holding no keys and no network. Several load-bearing details remain untested, chiefly Safari behaviour, BrowserPod under a service-worker header shim, and the eligibility of a hosted web app for OpenAI's programme.

*How to read the evidence: a statement followed by a link was read in a source during the November 2026 research. "(not re-verified)" marks a claim from background knowledge whose linked primary source was not re-fetched. "Inference" marks reasoning that no source states. The section before the conclusion lists what is still unverified.*

## Three tiers of in-browser execution, and only one reaches phones

The research found real precedents for an agent that lives entirely in a tab, and they sort cleanly by weight. Each step up buys compatibility with existing tools and costs portability, licensing freedom and mobile support.

| Tier | Examples | What runs | Needs | Licence and dependency | Mobile |
|---|---|---|---|---|---|
| 1. Browser primitives | Co-do, pi-web-ui, just-bash, almostnode, Beamhop's current sandbox | Model-written JS, WASM tools, a simulated bash over a virtual filesystem | Sandboxed iframe, workers | Open (just-bash Apache-2.0, almostnode MIT) | Works in principle on iOS (inference) |
| 2. Language runtimes in WASM | Pyodide, QuickJS-in-WASM, Wasmer/WASIX | Real Python or an isolated JS VM, selected packages | WASM; Wasmer also needs cross-origin isolation | Open | Pyodide yes; Wasmer untested |
| 3a. Node/Linux userland in WASM | BrowserPod, WebContainers, Nodepod, Vivari, OpenContainer | Node, npm, git, bash, stock agent CLIs | SharedArrayBuffer, cross-origin isolation, JSPI for BrowserPod | BrowserPod and WebContainers closed; clones MIT but unproven | BrowserPod: not on iOS/iPadOS |
| 3b. Full-system emulation | CheerpX/WebVM, v86, container2wasm, linux-wasm | Unmodified Linux binaries | Large disk images, a network relay | Mixed; CheerpX proprietary | Impractical |

**Tier 1 is where the closest architectural matches to Beamhop sit.** Paul Kinlan's Co-do argues that the three parts of an agent sandbox (filesystem, network, safe execution) are all covered by existing browser technology: a user-picked folder through the File System Access API, a CSP `connect-src` limited to the model providers, WASM tools run in a fresh worker per execution, and a "double iframe" to render untrusted model output ([aifoc.us](https://aifoc.us/the-browser-is-the-sandbox/)). Its author calls it "really a Chrome demo" and is not certain CSP blocks every path. pi-web-ui ships a JavaScript REPL tool that executes model-written code in a sandboxed iframe, plus IndexedDB storage for sessions and keys ([npm](https://www.npmjs.com/package/@mariozechner/pi-web-ui)). Vercel's just-bash is "a virtual bash environment with an in-memory filesystem, written in TypeScript and designed for AI agents", with no network by default and no ability to run binaries ([just-bash README](https://cdn.jsdelivr.net/npm/just-bash@2.14.0/README.md)), and bash-tool layers `bash`, `readFile` and `writeFile` tools and an experimental skills loader on top of it ([Vercel changelog](https://vercel.com/changelog/use-skills-in-your-ai-sdk-agents-via-bash-tool)). Beamhop's own sandbox already belongs here: `packages/app/src/agents/sandbox.ts` runs JavaScript and Pyodide in workers started inside a `sandbox="allow-scripts"` `srcdoc` iframe, so agent code has an opaque origin and cannot open Beamhop's IndexedDB.

**Tier 3a is the only route to stock agent CLIs, and BrowserPod is the only verified one.** BrowserPod is a "WebAssembly-native kernel, designed from scratch to run in the browser" that exposes Linux-compatible syscalls, runs each process in its own worker, executes Node on the browser's own JS engine and ships real git, bash, npm and pnpm ([BrowserPod deep dive](https://labs.leaningtech.com/blog/browserpod-deep-dive)). BrowserCode, built on it, runs "unmodified versions of Claude Code, Codex CLI and Pi" in beta ([browsercode README](https://github.com/leaningtech/browsercode)). No evidence was found of stock agent CLIs running on WebContainers, v86, container2wasm, Wasmer or almostnode, though that search was shallow. The costs are specific. BrowserPod requires WebAssembly JSPI (Chrome/Edge 137+, Firefox 153+, Safari 27+) and cross-origin isolation, and "agents and Node.js projects don't run on iOS or iPadOS in any browser" ([browsercode README](https://github.com/leaningtech/browsercode)). Since version 4.0 on 16 November 2026 the runtime is free for commercial use with "no usage limit, no fee, nothing metered" when loaded from Leaning Technologies' CDN, but self-hosting, vendoring or redistributing it requires an enterprise licence ([BrowserPod 4.0](https://labs.leaningtech.com/blog/browserpod-40)). Older sources describe metered pricing, an API key and a ten-hour session cap ([pricing policy](https://browserpod.pages.dev/pricing-policy)), and the BrowserCode README still asks self-hosters for an API key, so the terms moved within months and should be re-read at decision time.

**WebContainers is mature but its licence is the blocker.** StackBlitz states that "licensing is required for production usage of the API in a commercial, for-profit setting" with no published price ([webcontainers.io/enterprise](https://webcontainers.io/enterprise)), its acceptable use policy repeats the restriction ([StackBlitz AUP](https://stackblitz.com/acceptable-use-policy)), and its docs still list Firefox as alpha and Safari as beta ([browser support](https://webcontainers.io/guides/browser-support)). Whether a free, open-source, static app counts as commercial is unanswered. The 2026 open-source clones (Nodepod, Vivari, OpenContainer) describe themselves as MIT WebContainer alternatives ([Nodepod](https://github.com/ScelarOrg/Nodepod), [Vivari](https://github.com/atinux/vivari), [OpenContainer](https://github.com/imtia33/opencontainer)); their maturity was not assessed.

**Tier 3b runs anything, slowly, and always needs a relay.** WebVM runs an unmodified Debian userland on the proprietary CheerpX engine, which is free for individuals and FOSS projects only from Leaning Technologies' domain, and its networking requires joining a Tailscale network with an exit node ([WebVM](https://github.com/leaningtech/webvm), [CheerpX licensing](https://cheerpx.io/docs/licensing)). v86 emulates roughly a Pentium 4 with no 64-bit support ([v86](https://github.com/copy/v86)). container2wasm is Apache-2.0 and self-described as experimental ([container2wasm](https://github.com/container2wasm/container2wasm)). The native Linux-to-WASM port announced in November 2025 is a technology demo that boots BusyBox ([LWN](https://lwn.net/Articles/1044787/)). Inference: these suit "run one small native tool", not "run a Node-based agent".

Two platform constraints cut across tier 3. First, GitHub Pages cannot send COOP/COEP headers, so SharedArrayBuffer needs a service-worker shim such as coi-serviceworker, which reloads the page once ([coi-serviceworker](https://www.github.com/gzuidhof/coi-serviceworker)); Beamhop would have to merge that into its existing PWA worker, and isolation then applies to every cross-origin avatar and embed. Second, an iPhone's web content process is limited to about 1.5 GB and can be killed at the OS's discretion ([WebKit bug 269777](https://www2.webkit.org/show_bug.cgi?id=269777)). Inference: a worker-per-process Node runtime with `node_modules` in memory is a structural mismatch for iOS, so the exclusion is unlikely to lift soon. Networking is the third limit: browsers expose no raw sockets to ordinary pages, so every sandbox chooses between `fetch` (serverless, CORS-bound), a relay someone operates, or a VPN the user sets up ([BrowserPod 4.0](https://labs.leaningtech.com/blog/browserpod-40), [v86 networking](https://raw.githubusercontent.com/copy/v86/master/docs/networking.md)).

## An opaque-origin iframe protects keys; only CSP and a broker stop leaks

The isolation research reduces to one rule: **the only widely shipped primitive that takes untrusted code out of the host's origin is an iframe sandboxed without `allow-same-origin`, or one served from a different site.** MDN states that such a frame's content "is treated as being from a special origin that always fails the same-origin policy" ([MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)). Workers are not a boundary, because a worker runs in its creator's origin and can open the same IndexedDB ([MDN Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers), not re-verified). Same-realm language sandboxes are not one either: Figma found several vulnerabilities in its Realms shim that "could have allowed code inside the sandbox to escape" and moved to QuickJS compiled to WebAssembly ([Figma](https://www.figma.com/blog/an-update-on-plugin-security/)), and ShadowRealm is still an unshipped Stage 2.7 draft ([TC39](https://tc39.es/proposal-shadowrealm)). Fenced Frames are being removed from Chrome ([blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/c9w5uH3eSuo/)), and `credentialless` iframes are Chromium-only ([caniuse](https://caniuse.com/wf-iframe-credentialless)).

Beamhop's existing sandbox gets the first half right and leaves the second half open. Reading the code: the iframe has an opaque origin, so the Nostr key and provider sign-ins are unreachable by API. It carries no Content-Security-Policy, though, and its Python worker imports Pyodide from jsDelivr, so the frame has unrestricted network access. Inference: any workspace file or tool input handed to the sandbox can be sent anywhere by injected code, and so can anything the agent is talked into writing to a file first.

Every major product closes that gap the same way. Claude serves each artifact from its own `<uuid>.frame.claudeusercontent.com` origin under a header CSP with `connect-src 'self'`, and a security probe found fetch, XHR, WebSocket, image beacons and `sendBeacon` to an outside collector all blocked ([Pluto Security](https://pluto.security/blog/inside-claude-artifacts-how-your-agent-publishes-to-the-web/)). ChatGPT apps render in nested `web-sandbox.oaiusercontent.com` iframes ([Vercel](https://vercel.com/blog/running-next-js-inside-chatgpt-a-deep-dive-into-native-app-integration)). The MCP Apps specification makes the pattern mandatory: "The Host and the Sandbox MUST have different origins", with a default policy of `default-src 'none'` and `connect-src 'none'` ([MCP Apps spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/2026-01-26/apps.mdx)). In all of them the bridge to the host is a message-passing stub that holds no token.

A static site has three ways to approximate this, in rising strength. The first is a CSP `<meta>` tag injected ahead of any untrusted bytes in a `srcdoc` frame: Simon Willison tested in April 2026 that script inside a `sandbox="allow-scripts"` iframe cannot remove it in Chromium or Firefox, and that it persists when the frame navigates to a `data:` URI; Safari was not tested ([Simon Willison](https://simonwillison.net/2026/Apr/3/test-csp-iframe-escape/)). The second is a service worker that synthesises responses with real headers, which works only inside the worker's scope and not on a first or hard reload (inference from the coi-serviceworker technique). The third is a second static host on a different registrable domain serving a tiny sandbox-proxy page, which mirrors MCP Apps and is the only arrangement with a strong process-isolation story (inference; `pages.dev` and `netlify.app` support custom headers per their docs, not re-verified: [Cloudflare Pages headers](https://developers.cloudflare.com/pages/configuration/headers/)). Per-artifact subdomains need wildcard DNS and are out of reach on github.io; a fresh opaque origin per frame is the substitute.

Four further points shape the design. Inference: a complete exfiltration block also needs the host page's own `frame-src` to stop the frame navigating itself to an attacker URL, and no `allow-popups`, `allow-forms` or `allow-top-navigation` tokens. Inference: cross-origin isolation should never be enabled on the document that holds keys if untrusted code shares its process, since it hands that code SharedArrayBuffer-grade timers; this is in direct tension with tier-3 engines, which need isolation, and argues for hosting them in a separate isolated document. Third, `github.io` is on the Public Suffix List, so `beamhop.github.io/app` is same-origin with any other Pages site published under the same account ([Public Suffix List](https://publicsuffix.org/list/public_suffix_list.dat), not re-verified); a second repo with Pages enabled under that account could read Beamhop's IndexedDB. Fourth, an opaque-origin frame has no persistent storage, so the host must broker files; the Origin Private File System is the cross-browser substrate, while a real local folder through `showDirectoryPicker` works only in Chromium, with Mozilla negative and Apple opposed ([caniuse](https://caniuse.com/mdn-api_window_showdirectorypicker)).

## In a shared room, every allowed destination is an exfiltration channel

The security incidents collected are almost all the same failure, and it is not sandbox escape. No documented escape from WebContainers, BrowserPod, Claude's artifact frame or ChatGPT canvas was found (from limited searching). What recurs is data leaving through a permitted channel. In "Claude Pirate", Claude's code sandbox had egress allow-listed to Anthropic's API, and an injected prompt made it upload user data to the attacker's own Anthropic account through the Files API ([Embrace The Red](https://embracethered.com/blog/posts/2025/claude-abusing-network-access-and-anthropic-api-for-data-exfiltration)). Claude Code's CVE-2025-55284 leaked data through DNS requests made by commands on the no-approval list ([Embrace The Red](https://embracethered.com/blog/posts/2025/claude-code-exfiltration-via-dns-requests)). Markdown-image exfiltration still worked across products in 2026 ([Archestra](https://archestra.ai/blog/data-exfiltration-via-markdown-image)). In a prompt-injection test against Claude artifacts, the agent published `.env.local` contents in 10 of 85 attempts, entirely outside the browser boundary ([Pluto Security](https://pluto.security/blog/inside-claude-artifacts-how-your-agent-publishes-to-the-web/)).

Beamhop's model is the hard case. Simon Willison's "lethal trifecta" is private data, exposure to untrusted content, and the ability to communicate externally, and the only reliable defence is to avoid combining them ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Inference: an agent with room history, another member's message as its trigger, and a `web_fetch` tool holds all three. Anthropic's own guidance for Claude Code channels is blunt: "An ungated channel is a prompt injection vector", and gating must be on the sender's identity, because gating on the room "would let anyone in an allowlisted group inject messages into the session" ([Claude Code channels reference](https://code.claude.com/docs/en/channels-reference)). Shipping products avoid Beamhop's configuration altogether: Claude Tag runs one organisation-owned agent per channel ([Anthropic](https://www.anthropic.com/news/introducing-claude-tag)), and GitHub Copilot's remote control lets only the account that started a session steer it ([GitHub docs](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-remote-control)). "Everyone brings an agent that others can instruct" is a third, riskier model with no published threat analysis.

The implications that follow are inferences, but they follow directly. Beamhop has an advantage Slack bridges lack: every Nostr event is signed, so each context item can carry its author's public key, and instruction authority can be tied to a signer. Messages from members who are not authorised, all other agents' output, fetched pages, shared files and shared skills are data that can be read but cannot trigger tools. When someone other than the owner triggers a turn, Meta's "Rule of Two" applies: drop either the private data or the state-changing and outbound tools ([Simon Willison](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)). Tool approvals follow the Claude Code relay pattern, in which the approval reply is intercepted by the runtime and never reaches the model ([Claude Code channels reference](https://code.claude.com/docs/en/channels-reference)). The model-facing design is Cloudflare's code mode transplanted into the tab: generated code calls typed capability stubs, and the trusted side attaches credentials on the way out, "so the agent code never sees secret credentials directly" ([Cloudflare](https://blog.cloudflare.com/dynamic-workers)). Tier-3 engines complicate this: BrowserCode allow-lists npm, GitHub and the AI provider APIs ([browsercode README](https://github.com/leaningtech/browsercode)), each of which is a destination an attacker can hold an account on.

## Subscriptions without an extension: one sanctioned path, and it is not a chat plan

**As of late November 2026, no major provider offers an officially supported flow in which a hosted static web origin obtains subscription-backed inference tokens.** Three different blockers apply, and a CORS proxy fixes only one of them. The CORS results below come from preflight probes run on a single day through a proxy; they show what a browser would be allowed to send, not that an authenticated call succeeds.

| Provider | What a tab can do | Terms and enforcement | Verdict without an extension |
|---|---|---|---|
| OpenRouter | PKCE with "no client registration, no backend, no secrets required"; key exchange and inference send `access-control-allow-origin: *` ([OpenRouter docs](https://openrouter.ai/docs/guides/overview/auth/oauth)) | Officially supported | Works today; user-pays credits, not a chat plan |
| API keys (Anthropic, OpenAI, Gemini, xAI, Mistral, DeepSeek, Groq and others) | Inference endpoints accept cross-origin preflights; Anthropic requires the `anthropic-dangerous-direct-browser-access` header ([Simon Willison](https://simonwillison.net/2024/Aug/23/anthropic-dangerous-direct-browser-access)) | Supported | Works today |
| ChatGPT Go/Plus/Pro/Business | "Sign in with ChatGPT" uses PKCE with no secret and public `api.openai.com/v1/responses`, but the documented redirect is `http://127.0.0.1:1455/auth/callback` ([OpenAI SIWC docs](https://developers.openai.com/siwc/token-sharing-open-source/sign-in.md)) | Official programme since 29 September 2026 for open-source tools and selected partners; private `chatgpt.com/backend-api` endpoints are prohibited under it ([yage.ai](https://yage.ai/share/chatgpt-subscription-oauth-en-20261013.html)) | Closest to viable; a tab cannot receive a loopback redirect |
| GitHub Copilot | Inference endpoint is browser-callable; the device-code and token endpoints return 405 with no CORS headers ([probe target](https://github.com/login/device/code)) | Officially supported for OpenCode through a named partnership ([GitHub changelog](https://github.blog/changelog/2026-01-16-github-copilot-now-supports-opencode/)); no general third-party programme found | Needs a proxy for three token calls; permission unestablished |
| Google AI Pro/Ultra (Gemini CLI client) | Token and Cloud Code endpoints are reachable from a browser | Google suspended accounts that used the Gemini CLI/Antigravity client in third-party tools in February 2026, including paid Ultra subscribers ([The Register](https://www.theregister.com/2026/02/23/google_antigravity_compute_burden/), [Google AI forum](https://discuss.ai.google.dev/t/250-mo-ultra-subscriber-banned-without-warning-the-openclaw-mass-ban-wave-shows-a-systemic-failure-in-googles-developer-support/123015)) | Technically works; highest account risk |
| Claude Pro/Max | OAuth token endpoints return no CORS headers ([probe target](https://platform.claude.com/v1/oauth/token)) | Third-party developers are not permitted to offer Claude.ai login or route requests through consumer credentials; server-side blocks since 9 January 2026 ([WinBuzzer](https://winbuzzer.com/2026/02/19/anthropic-bans-claude-subscription-oauth-in-third-party-apps-xcxwbn/)) | Not permitted and not browser-callable |
| Kimi Code, Z.ai GLM plan | Plan-issued API keys | Kimi permits third-party tools ([Kimi Help Center](https://www.kimi.com/en-cn/help/kimi-code/membership-guide)); Z.ai is "strictly limited" to official tools ([Z.ai FAQ](https://docs.z.ai/devpack/faq)) | Kimi plausible, CORS untested; Z.ai no |

Two findings bear directly on what Beamhop ships now. The README offers Google sign-in with Gemini CLI's client as a no-extension option, which is the exact pattern behind Google's 403 suspensions. The Companion extension's ChatGPT path targets the Codex backend, and `chatgpt.com/backend-api/codex/responses` is both closed to foreign origins and prohibited under OpenAI's programme. Inference: both should be relabelled or retired in favour of sanctioned routes, since "use at your own risk" understates a documented ban wave.

Anthropic's position changed at least four times in 2026 and is the least certain. A reinstatement of third-party agent use through the Agent SDK with a separate credit pool was announced on 13 May ([VentureBeat](https://venturebeat.com/technology/anthropic-reinstates-openclaw-and-third-party-agent-usage-on-claude-subscriptions-with-a-catch)) and reported paused on 15 June by a third-party blog. Inference: none of those changes concerned a hosted web app holding OAuth tokens, so Beamhop's current stance (Claude subscriptions only through Claude Code on the bridge) stands.

Four routes get a subscription into a room without an extension, none of them clean. Inference throughout:

The first is **completing OpenAI's flow by hand**. The loopback redirect fails to load in a browser, but the authorisation code is in the address bar; a paste-the-URL step followed by a token exchange from the tab would be mechanically similar to BrowserCode's workaround, which uses a "copy code" flow because "the default browser login redirects to a localhost callback the pod cannot receive" ([browsercode README](https://github.com/leaningtech/browsercode)). `auth.openai.com/oauth/token` answered a preflight with `allow-origin: *`, but the endpoint the docs name was not probed, and whether OpenAI treats a hosted static page as an eligible open-source app is unknown. This is a spike, not a plan, and the question belongs with OpenAI.

The second is **running the official CLI in the tab**. BrowserCode shows Claude Code signing in with a copied code inside BrowserPod, so the vendor's own client, not Beamhop, holds the credential. Whether Anthropic regards Claude Code embedded in a third-party page as acceptable is unverified, and it is desktop-only.

The third is **inverting the relationship**: expose Beamhop as a remote MCP server or MCP App so the user's own claude.ai or ChatGPT session is the agent. MCP Apps lists Claude and ChatGPT as supporting clients ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/)). This stays inside sanctioned surfaces but needs an HTTPS endpoint, which static hosting cannot provide; the relay would see plaintext unless decryption happens inside the embedded UI; and the agent acts only when its owner prompts it. MCP sampling is not a way round this, having been deprecated in the 2026-07-28 specification ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog.md)).

The fourth is **a minimal proxy for Copilot's token calls only**, leaving prompts on the direct path. It adds a server and an unanswered permission question.

Bookmarklets, popups and iframe tricks against provider web apps are dead ends: no provider is known to offer a `postMessage` inference API, and automating a consumer UI is the category providers enforced against. For users with no account at all, Chrome's Prompt API has been stable since Chrome 148 on desktop only, needs 22 GB of free disk and has no native tool calling ([Chrome docs](https://developer.chrome.com/docs/ai/prompt-api)); it is an opportunistic fallback.

## Outside the box: lend a workspace, mount a folder, keep the bridge optional

**Borrow a room member's sandbox.** No existing product was found in which one desktop member hosts the heavy workspace and others use it over the room; it looks like open design space. The pieces exist. just-bash includes a `Sandbox` class that is API-compatible with `@vercel/sandbox` ([just-bash README](https://cdn.jsdelivr.net/npm/just-bash@2.14.0/README.md)), which gives a seam for swapping a local virtual shell for a remote one. sshx demonstrates an end-to-end encrypted shared terminal where "the server never sees what you're typing" ([sshx](https://github.com/ekzhang/sshx/)), and Trystero already does WebRTC matchmaking over Nostr relays with encrypted offers ([Trystero](https://github.com/dmotz/trystero)). ContextVM carries MCP JSON-RPC over Nostr events, so tools are addressed by public key with no HTTP endpoint ([ContextVM SDK](https://docs.rs/crate/contextvm-sdk/0.1.1)). Inference: a desktop tab running BrowserPod exposes `bash`, `readFile` and `writeFile` to the room, phones use it, and the host sees plaintext and needs caps. The residual is TURN for restrictive networks, where Cloudflare's free 1,000 GB a month requires an account and credential minting ([Cloudflare Realtime pricing](https://developers.cloudflare.com/realtime/pricing/)); Nostr ephemeral events are the slower zero-infrastructure fallback.

**Share files as data, keep execution single-host.** No surveyed library offers an end-to-end encrypted, serverless, multi-writer filesystem. Keyhive and Beelay are the closest conceptual fit and are pre-alpha ([Ink & Switch](https://www.inkandswitch.com/newsletter/dispatch-010)), Jazz needs a sync server ([Jazz docs](https://jazz.tools/docs/sync-and-storage)), and tldraw sync is server-authoritative ([tldraw](https://tldraw.dev/docs/sync)). Inference: treat file updates as opaque bytes under the existing room key, and treat processes as state on one host that is streamed and periodically snapshotted to Blossom so another device can resume the files. MLS through Marmot was audited in 2026 ([Least Authority](https://leastauthority.com/blog/audit-of-white-noise-marmot-development-kit-mdk/)) but brings little at 50 members.

**Mount a local folder with no local process.** The File System Access API is the only true zero-install bridge to a user's files, and it is Chromium-only; `<input type="file" webkitdirectory>` gives a read-only copy elsewhere ([web.dev](https://web.dev/patterns/files/open-a-directory)). Inference: a mounted folder shared into a room is a privilege escalation that deserves its own consent, owner-only by default.

**Attach user-owned compute.** Hosted sandboxes all need an operator account, so they fit only as bring-your-own. GitHub Codespaces includes 120 core-hours a month on free personal accounts ([GitHub Docs](https://docs.github.com/en/billing/concepts/product-billing/github-codespaces)); whether a browser origin can create and reach one was not verified.

**Accept that tabs sleep.** Chrome throttles timers in hidden tabs to once a minute after about five minutes, exempting tabs with live WebSocket or WebRTC connections ([Chromium blog](https://blog.chromium.org/2020/11/tab-throttling-and-more-performance.html), [Chrome](https://developer.chrome.com/blog/background_tabs)), and iOS suspends pages shortly after backgrounding. Vendors solve this with a cloud runner or a local process plus relay ([Zed Delta](https://zed.dev/blog/introducing-delta), [Claude Code Remote Control](https://code.claude.com/docs/en/remote-control)). Inference: Beamhop's queue-and-resume is the honest default, an owner's other device is the first upgrade, and a member-run always-on peer that holds a workspace replica but no model credentials is the low-trust second.

**The desktop bridge stays secondary and mostly as it is.** A page-to-localhost link now costs a permission prompt in Chrome 142+ and Firefox 151+ ([Chrome](https://developer.chrome.com/blog/local-network-access), [Mozilla](https://support.mozilla.org/en-US/kb/control-personal-device-local-network-permissions-firefox)) and has a long record of being blocked in Safari ([WebKit bug 171934](https://bugs.webkit.org/show_bug.cgi?id=171934)), so it is a fast path, not the primary link. Claude Code, Copilot CLI and Codex each offer first-party remote control bound to the vendor account, with no third-party API found. Claude Code channels would let room mentions start a turn in a desktop session and relay approvals to a phone, but custom channels need `--dangerously-load-development-channels` during the research preview ([Claude Code channels reference](https://code.claude.com/docs/en/channels-reference)). The existing Nostr-outbound `npx` bridge is the same shape as Anthropic's own Telegram and Discord channels, and remains the right design.

## Recommended architecture and phased path

This section is a recommendation and therefore inference, built on the evidence above.

The architecture has four parts. A **trusted core** on Beamhop's origin holds keys, the Nostr client, the agent loop (fx in WASM today) and a capability broker; it is the only code that calls model providers, MCP servers or the web. A **universal sandbox** runs all model-written code with no network and no secrets: opaque-origin iframe, strict CSP, worker per run, Pyodide and a JS runtime, a virtual shell, and a virtual filesystem the core serves from OPFS. A **full workspace** is an optional desktop capability: a tier-3 engine in a separate cross-origin-isolated document, reachable by other members through room-addressed tools. **Provider access** defaults to sanctioned routes. Each agent turn carries the signer of its trigger, and tools are granted per trigger, not per room.

**Phase 0, harden what ships (days to two weeks).** Add a CSP to the existing sandbox frame with `connect-src 'none'`, and deliver Pyodide through the host instead of letting the sandbox fetch it. Add `frame-src` to the host page. Stop auto-rendering remote images and links in agent output. Tag context with author keys and make non-owner triggers lose either private context or outbound tools. Keep the GitHub account free of other Pages sites or move to a custom domain. Relabel or remove the Gemini CLI sign-in, and review the Codex-backend path.

**Phase 1, make the universal sandbox feel like a computer (weeks).** Add a just-bash-style shell and skills as file bundles, back files with OPFS, and put a single tab in charge through Web Locks. Move the sandbox to a second static origin with real headers once Safari results are in. Offer folder mount on Chromium and copy-in elsewhere. This is the tier that works for every member, so it carries the main goal.

**Phase 2, subscriptions through sanctioned doors (parallel).** Lead with OpenRouter and keys. Ask OpenAI whether a hosted open-source web app qualifies for Sign in with ChatGPT, and spike the paste-the-URL exchange only if the answer permits it; implement the documented loopback flow in the bridge regardless. Treat a Copilot token proxy as a later, opt-in, self-hostable item pending GitHub's position.

**Phase 3, full workspace as a lendable capability (one to two months, gated on spikes).** Prototype BrowserPod in an isolated document under a service-worker header shim on GitHub Pages; if it works, expose it through a `Sandbox` interface over the room, with host-side caps and an egress allowlist treated as leaky. Keep the interface engine-neutral so an MIT clone or a self-hosted licence can replace the CDN dependency. Add Blossom snapshots for device handover.

**Phase 4, optional servers and desktop reach.** TURN credential minting, an always-on replica peer, a self-deployed remote-MCP shim, and a Claude Code channel plugin if custom channels open up. None is required for the browser-first goal.

The steelman for the opposite choice, adopting BrowserPod as the single sandbox, is real: it is the only thing that runs stock CLIs and it is now free. It fails Beamhop's own constraints on three counts: phones are excluded, the runtime is a closed third-party dependency that cannot be self-hosted without a licence, and it requires cross-origin isolation on a page that holds keys.

## What remains unverified

The following were not confirmed and several could change the plan. Safari was not covered by the meta-CSP tamper test, and WebKit's Site Isolation status on iOS and macOS is unknown, so the strength of any iframe boundary on iPhones is untested. Whether Chrome process-isolates same-site sandboxed frames on all platforms was not checked. BrowserPod was never loaded or measured: startup time, memory, Android behaviour, whether it works under a service-worker header shim, whether its fetch network supports the WebSockets a Nostr client needs, and how BrowserCode reaches provider APIs are all open, and its community licence text was not read. No quantitative performance figures were found for any engine. All CORS results are single-day preflights without authenticated requests. Anthropic's rule after June 2026 was not confirmed from a primary page. OpenAI's eligibility criteria and hosted-redirect rules were not found, and the documented token endpoint was not probed. No official GitHub statement covers Copilot clients beyond named partners. Licences of just-bash, bash-tool, AgentFS and pi were taken from secondary pages. Nostr relay rate limits for real-time workspace traffic at 50 members were not measured. Codespaces access from a browser origin, ContextVM's maturity, and whether WebMCP shipped on schedule were not verified. The absence of prior art for peer-lent sandboxes and of documented sandbox escapes comes from limited searching.

## Conclusion

The framing of "which Linux-in-the-browser should Beamhop adopt" turns out to be the wrong question. The engines are the easy part and the least portable part; the work that determines whether strangers can safely share a room with each other's agents is the broker that sits between a keyless sandbox and everything valuable, and Beamhop's signed-event transport gives it better provenance for that broker than any chat platform the big vendors have built on. That inverts the usual priority: sandbox size is a feature to add per device, while authority per signer is the foundation.

The subscription question has a similar shape. The market moved in 2026 from tolerated reuse of CLI clients to explicit programmes and explicit bans, and the durable position is to be on the sanctioned side of each provider's line, even where that means a paste step, a bridge, or a different way to pay. The one genuinely new product idea in the evidence is lending: a desktop member's full workspace, addressed by key over the room, used by a phone. Nothing found does this today, and Beamhop already has the identity, encryption and transport it needs.
