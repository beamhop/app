## 1. Browser-run agent products and prior art: what exists, where the loop runs, where code executes, how the LLM is reached

### Takeaway
There are now several real "agent fully in a tab" precedents — Leaning Technologies' BrowserCode/BrowserPod (runs unmodified Claude Code / Codex CLI / Pi inside a WebAssembly Node sandbox), Paul Kinlan's Co-do (browser-primitive sandbox: File System Access + CSP + double iframe + WASM-in-Worker tools), pi-web-ui (browser agent UI with iframe-sandboxed JS REPL and artifacts), Alibaba page-agent (in-page DOM agent, no extension), and Mozilla.ai wasm-agents (Pyodide) — but the mainstream commercial products split into "browser executes code but the agent loop and keys are server-side" (bolt.new) and "everything in cloud containers" (Lovable, OpenCode, Copilot). The closest fits for a static BYOK PWA are the Co-do pattern and the pi-web-ui pattern (pure browser primitives, MIT-style licensing), with BrowserPod/WebContainers as heavier, vendor-keyed, non-iOS options.

**Paul Kinlan — Co-do ("the browser is the sandbox", Jan 2026)**
- Thesis: the three parts of an agent sandbox — filesystem, network, safe code execution — can all be handled with existing browser tech. Co-do is a Claude-Cowork-like app that runs in the tab. *(fetched)* — [Simon Willison, 25 Jan 2026](https://simonwillison.net/2026/Jan/25/the-browser-is-the-sandbox/); [original post](https://aifoc.us/the-browser-is-the-sandbox/)
- Architecture *(fetched)* — [aifoc.us](https://aifoc.us/the-browser-is-the-sandbox/):
  - LLM: user picks Anthropic, OpenAI or Google and supplies a key; the page calls the provider directly; CSP is `connect-src 'self'` plus those three provider endpoints.
  - Filesystem: File System Access API scoped to a user-selected folder handle ("chroot-like"); granular write permission (always / ask / never). Safari lacks `showDirectoryPicker`.
  - Code execution: custom tools are WebAssembly modules run in Web Workers; a fresh Worker per execution, terminable on timeout; workers inherit the CSP. Pre-compiled WASM binaries for text/file ops; ffmpeg planned.
  - Rendering untrusted model output: "double iframe" — outer iframe (`sandbox="allow-scripts"`, `srcdoc`) carries a restrictive CSP starting from `default-src 'none'` as a "policy firewall"; inner iframe (`sandbox=''`) holds the LLM output. Costs: separate origin blocks auto-sizing, careful `srcdoc` escaping, two DOMs per embed.
  - The `csp` attribute on iframes works only in Blink browsers.
- Stated unsolved problems *(fetched)* — [aifoc.us](https://aifoc.us/the-browser-is-the-sandbox/): author not certain CSP blocks every path (Beacon, DNS prefetch); file contents go to a third-party provider; generated files can be dangerous once opened outside the browser; no undo/backup; permission-prompt fatigue; provider-side tools such as web search may open new exfiltration paths; "really a Chrome demo". Source at github.com/PaulKinlan/Co-do (license not stated on the page).
- Simon Willison's comments: `<iframe sandbox>` remains thinly documented across browsers; File System Access is Chrome-only as far as he can tell; `<input type="file" webkitdirectory>` gives read-only whole-directory access in Firefox, Safari and Chrome. *(fetched)* — [simonwillison.net](https://simonwillison.net/2026/Jan/25/the-browser-is-the-sandbox/)

### Inferences
- Three distinct architectural tiers exist for "code execution in a tab", in increasing weight and decreasing portability:
  1. **Browser primitives** (sandboxed iframe JS REPL, Workers, WASM tools, virtual FS) — Co-do, pi-web-ui, just-bash. Works on mobile Safari in principle (no JSPI, no cross-origin isolation needed), tiny, MIT/Apache. Cannot run arbitrary binaries or real npm/pip.
  2. **Language runtimes in WASM** (Pyodide, QuickJS, Wasmer packages) — wasm-agents, Wasmer SDK. Real Python, but limited package/network story.
  3. **Full Node/Linux in WASM** (WebContainers, BrowserPod, Nodepod/Vivari/OpenContainer) — can run unmodified agent CLIs, but need JSPI/SharedArrayBuffer-class features, exclude iOS (BrowserPod explicitly), and the two mature engines are proprietary/keyed with commercial restrictions.
- For Beamhop (static PWA on GitHub Pages, mobile members, E2EE), tier 1 is the only tier that plausibly works for every room member; tier 3 fits better as an *optional* capability provided by a desktop member (see §5).
- BrowserCode proves that porting the harness is unnecessary if you accept a vendor engine: unmodified Claude Code/Codex/Pi run in a tab. The cost is a BrowserPod API key (vendor dependency, metered pricing, 10-hour cap, allowlisted egress presumably via vendor networking) and no iOS.
- GitHub Pages cannot set COOP/COEP headers, so anything requiring cross-origin isolation (SharedArrayBuffer — WebContainers and several Node-in-browser runtimes) would need a service-worker header shim; I did not verify which of the 2026 runtimes need it (see Gaps).
- "Viewer pays" LLM access exists in two walled forms — Claude artifacts (`window.claude.complete`) and Puter's user-pays — neither is usable from an arbitrary static origin without adopting the vendor's platform (Puter) or living inside claude.ai (artifacts). For Beamhop the realistic LLM path is BYOK direct-to-provider over CORS.

## 2. JS/TS agent harnesses that are browser-compatible or portable; virtual filesystem + virtual shell building blocks

### Takeaway
The Vercel AI SDK's `ToolLoopAgent` is documented as running entirely in the browser (via `DirectChatTransport`), and pi's stack already ships a browser UI package; combined with just-bash (in-memory bash + FS, runs in browser), bash-tool (bash/readFile/writeFile tools + experimental skills) and AgentFS (SQLite-backed FS with OPFS persistence in browser), the pieces for a no-server "Claude-Code-shaped" agent in a tab exist as permissively published npm packages. OpenAI's Agents SDK officially targets Node/Deno/Bun (browser only for realtime voice), and no source confirmed browser support for Claude Agent SDK, Mastra, LangGraph.js or Effect AI.

### Cited Findings

**Harnesses**
- Vercel AI SDK: Chrome's developer blog documents running the loop client-side with no backend — `useChat` with `DirectChatTransport` "runs the ToolLoopAgent loop entirely in the browser with no server involved" (their example uses Chrome's built-in Prompt API with cloud fallback). *(snippet)* — [Chrome for Developers](https://developer.chrome.com/blog/prompt-ui-ai-elements-with-vercel-ai)
- AI SDK 6 introduced the agent abstraction (ToolLoopAgent); AI SDK 7 is released and lists experimental browser-to-provider WebSocket sessions with client-driven tool calls. *(snippet)* — [AI SDK 6](https://vercel.com/blog/ai-sdk-6); [AI SDK 7 changelog](https://vercel.com/changelog/ai-sdk-7)
- A long-standing AI SDK issue about Anthropic direct-browser access exists (CORS header support in the provider). *(snippet)* — [vercel/ai #3041](https://github.com/vercel/ai/issues/3041)
- OpenAI Agents SDK (JS/TS): officially supported environments are Node.js 22+, Deno and Bun, with Cloudflare Workers experimental; browser use is positioned around realtime voice agents via a separate browser-optimised package using short-lived ephemeral tokens minted by your server. *(snippet)* — [openai/openai-agents-js](https://github.com/openai/openai-agents-js); [docs](https://openai.github.io/openai-agents-js/)
- pi-agent-core: agent runtime (tool calling, state) consumed by the browser package pi-web-ui, which implies the core loop is browser-compatible. *(snippet)* — [pi-web-ui npm](https://www.npmjs.com/package/@mariozechner/pi-web-ui)
- OpenAI Agents SDK *Python* runs in-browser under Pyodide (Mozilla wasm-agents). *(snippet)* — [Mozilla.ai](https://blog.mozilla.ai/wasm-agents-ai-agents-running-in-your-browser/)

**Virtual shell / filesystem**
- just-bash (vercel-labs): "a virtual bash environment with an in-memory filesystem, written in TypeScript and designed for AI agents"; beta; no network by default; cannot run binaries (docs point to Vercel Sandbox for a full VM); filesystem modes include in-memory, overlay (read from disk, writes stay in memory) and read-write; includes a `Sandbox` class API-compatible with `@vercel/sandbox`. *(snippet)* — [just-bash README](https://cdn.jsdelivr.net/npm/just-bash@2.14.0/README.md); [Better Stack guide](https://betterstack.com/community/guides/ai/just-bash-simulated/)

- Versions seen: 2.14.0 README on jsDelivr and 3.0.2/3.0.3 on Socket — a 3.x major exists; check the current API. Community ports exist in Python (PyPI `just-bash`) and Rust (`vbash`). *(snippet)* — [Socket 3.0.3](https://socket.dev/npm/package/just-bash/overview/3.0.3); [PyPI](https://pypi.org/project/just-bash/0.2.1/); [docs.rs vbash](https://docs.rs/crate/vbash/0.1.0)

- h5i-agent's browser build pairs an in-memory FS with optional user-selected-folder access. *(snippet)* — [Medium](https://medium.com/@Koukyosyumei/i-built-a-130-kb-webassembly-coding-agent-harness-that-runs-in-browsers-and-terminals-ceae7a3516f2)

### Inferences
- A minimal Beamhop harness stack that needs no vendor key: AI SDK `ToolLoopAgent` (or pi-agent-core) in a Worker → provider over CORS with user key → tools = just-bash over an in-memory/OPFS FS + iframe/Worker JS REPL + (optional) Pyodide. This matches how Co-do and pi-web-ui are built and avoids WebContainers/BrowserPod licensing entirely.
- just-bash's `Sandbox` class being API-compatible with `@vercel/sandbox` suggests a clean abstraction seam: the same agent code can target the in-tab virtual shell or a remote real sandbox (a room member's machine, a user-owned cloud sandbox) by swapping the implementation.
- AgentFS's single-tab OPFS lock matters for a PWA that users open in multiple tabs/windows; a SharedWorker/leader-election design or a non-SQLite FS would be needed.
- Because OpenAI's Agents SDK does not list browsers as a supported runtime (outside realtime), choosing it would mean owning the port; AI SDK and pi are the safer bets.

### Gaps
- No source found confirming browser compatibility of Claude Agent SDK (TS), Mastra, LangGraph.js or Effect AI. No source this session on ZenFS, memfs, lightning-fs or isomorphic-git.
- Licenses of just-bash, bash-tool, AgentFS and AI SDK were not confirmed from primary pages this session.
- Whether just-bash 3.x still bundles optional WASM runtimes (Python/JS/SQLite) usable in-browser was not verified.
- **Unverified background (leads):** Claude Agent SDK (TypeScript) spawns/bundles the Claude Code CLI and needs Node-style process + filesystem — not browser-runnable except inside a Node-in-WASM engine (consistent with BrowserCode running Claude Code in BrowserPod); AI SDK core and provider packages are Apache-2.0 and fetch-based; `@ai-sdk/anthropic` exposes a header option for direct browser access; LangGraph.js has a `/web` entrypoint without `async_hooks`; Mastra is server-oriented (Node, storage adapters) with a browser *client* SDK; isomorphic-git (MIT) + lightning-fs or ZenFS (IndexedDB/OPFS backends) give git clone/commit in-browser but need a CORS proxy for most git hosts; memfs is an in-memory Node `fs` implementation usable in browsers; just-bash and bash-tool are Apache-2.0; AgentFS is MIT.

## 3. MCP in the browser: clients over Streamable HTTP, in-page servers (WebMCP / MCP-B), OAuth from a static site (DCR vs CIMD)

### Takeaway
A static PWA can be an MCP client, but only against servers that deliberately allow it: the server must send CORS headers and expose `Mcp-Session-Id`, and for OAuth the current MCP spec deprecates Dynamic Client Registration in favour of Client ID Metadata Documents — a JSON file at an HTTPS URL, which a GitHub Pages site can host. In-page MCP ("WebMCP") is in a Chrome origin trial (M149–M156, shipping targeted M157) with an API surface still changing; MCP-B's polyfill packages work today.

### Cited Findings
- Browser clients using the TypeScript SDK's `StreamableHTTPClientTransport` cannot keep a session unless the server exposes the header: the SDK docs add a CORS section using `exposedHeaders: ['Mcp-Session-Id']` and allowing `mcp-session-id` and `mcp-protocol-version` request headers. A reported issue showed a browser client failing to persist the session ID where Node worked. *(snippet)* — [typescript-sdk issue #764](https://github.com/modelcontextprotocol/typescript-sdk/issues/764); [Python SDK PR #1059](https://github.com/modelcontextprotocol/python-sdk/pull/1059); [TS SDK v2 StreamableHTTPClientTransport docs](https://ts.sdk.modelcontextprotocol.io/v2/api/@modelcontextprotocol/client/client/streamableHttp.html)
- Some servers also need to expose `WWW-Authenticate` and `mcp-protocol-version` for browser clients (needed for OAuth discovery from a 401). *(snippet)* — [barrel_mcp docs](https://hexdocs.pm/barrel_mcp/http-stream.html)
- mcp-proxy (open source) bridges MCP servers to HTTP and exposes `Mcp-Session-Id` by default — a common shim for non-CORS servers. *(snippet)* — [mcp-proxy README](https://unpkg.com/mcp-proxy@6.6.0/README.md)
- The MCP TypeScript SDK has a v2 with a separate `@modelcontextprotocol/client` package. *(snippet)* — [TS SDK v2 docs](https://ts.sdk.modelcontextprotocol.io/v2/api/@modelcontextprotocol/client/client/streamableHttp.html)
- OAuth registration: the MCP spec says Dynamic Client Registration is deprecated and new implementations should use Client ID Metadata Documents; clients and authorization servers SHOULD support CIMD; the client uses an HTTPS URL as `client_id` which serves a JSON metadata document; the authorization server fetches it, MUST check the document's `client_id` matches the URL exactly, and caches per HTTP headers; servers advertise `client_id_metadata_document_supported`. *(snippet)* — [MCP spec: client registration](https://modelcontextprotocol.io/specification/latest/basic/authorization/client-registration); [WorkOS explainer](https://workos.com/blog/client-id-metadata-documents-cimd-oauth-client-registration-mcp); [Auth0: CIMD vs DCR](https://auth0.com/blog/cimd-vs-dcr-mcp-registration/)
- MCP spec revision 2026-07-28 normatively references CIMD draft-00 (per one source); CIMD is still an IETF draft and implementations differ by draft version. *(snippet)* — [Stytch](https://stytch.com/blog/oauth-client-id-metadata-mcp/)
- Authorization-server support is spreading in 2026: Clerk (Aug 2026), Descope, Ping Identity, better-auth, ServiceNow, GitLab (issue tracking SEP-991). *(snippet)* — [Clerk changelog](https://clerk.com/changelog/2026-08-05-client-id-metadata-documents); [better-auth CIMD plugin](https://better-auth.com/docs/plugins/cimd); [GitLab issue](https://gitlab.com/gitlab-org/gitlab/-/issues/585070)
- Ping Identity's docs note CIMD documents can't set JavaScript origins — potentially relevant to browser (SPA) clients' token-endpoint CORS on that vendor. *(snippet)* — [PingOne docs](https://docs.pingidentity.com/pingoneaic/am-oauth2/oauth2-cimd.html)
- WebMCP: Chrome "Intent to Experiment" — origin trial M149 through M156, shipping on desktop targeted for M157; spec incubating, TAG review to be requested before shipping. *(snippet)* — [blink-dev Intent to Experiment](https://groups.google.com/a/chromium.org/g/blink-dev/c/gmYffo5WOE8)
- API name in flux: a Chromium change synced to WPT removes `navigator.modelContext` in favour of `document.modelContext`. *(snippet)* — [Mozilla bug 2053854](https://bugzilla.mozilla.org/show_bug.cgi?id=2053854)
- Chrome's guidance distinguishes when to use WebMCP (tools a page exposes to a browser's agent) vs MCP. *(snippet)* — [Chrome for Developers](https://developer.chrome.com/blog/webmcp-mcp-usage)
- MCP-B is a separate open-source project providing interoperability between WebMCP-formatted tools and MCP clients, with npm packages (polyfill, transports) usable today; guides advise not relying on the native API in production yet. An MCP-B browser extension exists but the npm packages are independent of it. *(snippet)* — [WebMCP-org/npm-packages](https://github.com/WebMCP-org/npm-packages); [StudioMeyer reality check, May 2026](https://studiomeyer.io/en/blog/webmcp-reality-check-may-2026); [Arcade interview with Alex Nahas](https://www.arcade.dev/blog/web-mcp-alex-nahas-interview)
- Claude artifacts support MCP (Oct 2025) — an existence proof of sandboxed front-end code using MCP tools, though via Anthropic's backend. *(snippet)* — [claude.com/blog/build-artifacts](https://claude.com/blog/build-artifacts)

### Inferences
- For Beamhop, the CIMD model is unusually favourable: `https://<pages-domain>/client-metadata.json` can be the `client_id`, so no registration backend is needed. The remaining browser-specific blockers are on the *server* side: CORS on the MCP endpoint, on the authorization-server metadata/token endpoints, and exposed `Mcp-Session-Id`/`WWW-Authenticate`. Expect a meaningful fraction of public remote MCP servers to fail one of these from a browser; a user-supplied CORS proxy (or a desktop room member relaying) is the fallback.
- A public (PKCE, no secret) client from a static origin means tokens live in the page; in an agent context this puts OAuth tokens inside the prompt-injection blast radius unless the MCP client runs in a separate origin/Worker that the agent's code-execution sandbox cannot read.
- WebMCP is aimed at *pages exposing tools to the browser's own agent*, the inverse of Beamhop's need (a page hosting its own agent). The more useful piece for Beamhop is in-page MCP transports (MCP-B's tab/postMessage transports, SDK in-memory transport) to connect in-tab "servers" (e.g. WASM tools, the virtual FS) to the in-tab agent with standard MCP semantics.
- Mixed content: a GitHub Pages (HTTPS) page generally cannot call plain-HTTP MCP servers except loopback, so "local MCP server on my desktop" requires localhost + permissive CORS on that server.

### Gaps
- Did not verify from the CIMD draft whether the authorization server fetches the metadata server-side (expected; would mean no CORS needed on the JSON file) and whether GitHub Pages' content-type/caching is acceptable.
- Found nothing first-hand on `use-mcp` (browser React MCP client), wasm-compiled MCP servers, or how many popular remote MCP servers send browser-compatible CORS.
- WebMCP current stable status in Chrome as of Nov 2026 (which milestone is stable now) not verified.
- **Unverified background (leads):** the MCP TS SDK ships `InMemoryTransport.createLinkedPair()` for same-process client/server; the SDK's client OAuth helper (`auth()` / `OAuthClientProvider`) is browser-usable and was originally demonstrated in browser-based tools such as MCP Inspector and Cloudflare's AI playground; `use-mcp` handles the OAuth popup flow in React; MCP Apps (SEP-1865) standardise UI resources rendered in sandboxed iframes.

## 4. Skills / plugin formats usable in-browser

### Takeaway
Agent Skills (a directory with `SKILL.md` — YAML frontmatter `name`/`description` plus markdown instructions, optional scripts — loaded by progressive disclosure) are just files, so they work against any virtual filesystem; Vercel's bash-tool already ships an experimental skills tool on top of just-bash, which is the nearest ready-made in-browser path. No source showed a production in-browser skills runtime.

### Cited Findings
- Vercel changelog: "Use skills in your AI SDK agents via bash-tool" — skills support gives AI SDK agents the skills pattern with filesystem context, bash execution and sandboxed runtime access; a `ToolLoopAgent` example passes skill files into the bash tool. *(snippet)* — [Vercel changelog](https://vercel.com/changelog/use-skills-in-your-ai-sdk-agents-via-bash-tool)
- bash-tool exports an experimental `createSkillTool` that discovers skills from a directory; instruction-only skills can run without bash; SKILL.md should hold only frontmatter and instructions when there are no scripts. *(snippet)* — [bash-tool docs](https://docsearch.algolia.com/mcp/docs/repo/vercel-labs/bash-tool)
- Default just-bash cannot run binaries such as Python or Node, so skills that ship `.py`/Node scripts need a real runtime (docs suggest `@vercel/sandbox`). *(snippet)* — [bash-tool docs](https://docsearch.algolia.com/mcp/docs/repo/vercel-labs/bash-tool)
- Agent Skills is a documented open format (agentskills.io); the pattern relies on progressive disclosure — only a compact catalogue (name + description) is loaded at startup. Other frameworks (e.g. Haystack) implement the same SKILL.md directory format. *(snippet)* — [agentskills.io llms-full.txt](https://agentskills.io/llms-full.txt); [Haystack cookbook](https://haystack.deepset.ai/cookbook/computer_use_agent_with_skills)
- WebMCP tooling is itself being distributed as skills (skills.sh entries), showing the format's spread across harnesses. *(snippet)* — [skills.sh webmcp-polyfill](https://www.skills.sh/orcaqubits/agentic-commerce-skills-plugins/webmcp-polyfill)

### Inferences
- In Beamhop, a skill can be shipped as a small file bundle (even as encrypted Nostr events/blobs shared in a room), mounted into the agent's virtual FS, with the catalogue injected into the system prompt. Instruction-only skills work everywhere; script-bearing skills work only where a matching runtime exists (bash scripts → just-bash; Python → Pyodide; Node → needs a tier-3 engine or a borrowed sandbox).
- Skills shared between room members are untrusted input: a SKILL.md is a prompt-injection vector by design, so skill installation should be an explicit, per-user trust decision.

### Gaps
- No source on Claude Code plugin format, MCP Apps, or other plugin formats running in-browser.
- Did not confirm whether `createSkillTool` is still experimental in the current bash-tool release.

## 5. Outside-the-box compute: server-side sandboxes, user-owned free compute a web page can attach to, peer-to-peer "borrow a room member's sandbox"

### Takeaway
Hosted sandboxes (E2B, Daytona, Modal, Cloudflare, Vercel) all require an operator account and cost roughly $0.05–0.13 per vCPU-hour with modest free credits, so they only fit Beamhop as "user brings their own sandbox account/key". GitHub Codespaces is the most concrete free user-owned option (120 core-hours/month on personal Free accounts). I found no existing product doing the peer-to-peer "one desktop member hosts the VM, others use it over WebRTC" pattern — it appears to be open design space, with BrowserPod/WebContainer-class engines as the natural host-side component.

### Cited Findings
- E2B: free Hobby tier limited to 1-hour continuous runtime and 20 concurrent sandboxes; Pro $150/month. Daytona: one source says one-time $100 credit, another $200; Pro $150/month. Modal: $30/month free compute; sandbox rate ≈3× standard function rate. Cloudflare Sandbox/Containers: requires the $5 Workers Paid plan, including 375 vCPU-minutes, 25 GiB-hours memory, 200 GB-hours disk per month. Vercel Sandbox: active-CPU billing. Normalised cost per vCPU-hour in one comparison: E2B $0.0504, Modal ≈$0.071, Cloudflare ≈$0.072, Vercel $0.128. **All from third-party 2026 comparison blogs that disagree with each other — verify on vendor pages.** *(snippet)* — [Superagent benchmark 2026](https://www.superagent.sh/blog/ai-code-sandbox-benchmark-2026); [Upstash comparison](https://upstash.com/blog/ai-agent-sandbox-providers-compared-2026.md); [Fly.io pricing explainer](https://fly.io/learn/ai-sandbox-pricing/); [Northflank](https://northflank.com/blog/ai-sandbox-pricing)
- GitHub Codespaces included usage for personal accounts: GitHub Free 120 core-hours + 15 GB-month storage per month; Pro 180 core-hours + 20 GB-month. 120 core-hours = 60 clock hours on a 2-core machine. With no payment method, Codespaces is blocked when the quota runs out. Organisation/enterprise plans include no free quota. *(snippet)* — [GitHub Docs: Codespaces billing](https://docs.github.com/en/billing/concepts/product-billing/github-codespaces); [GitHub blog 2022](https://github.blog/changelog/2022-11-09-codespaces-for-free-and-pro-accounts/)
- GitHub Copilot cloud sandbox usage starts billing Nov 2026, with free usage drawing from a shared compute entitlement. *(snippet)* — [VS Code Copilot FAQ](https://code.visualstudio.com/docs/copilot/faq)
- Puter's user-pays model is an existing example of "each end user's own account funds compute/AI for a front-end-only app". *(snippet)* — [Puter docs](https://docs.puter.com/user-pays-model/)
- Client-side engines are positioned by their vendors precisely as the zero-server-cost alternative: BrowserPod ("no servers, no cloud compute"), Bolt's WebContainers removing the per-session VM bill. — [leaningtech/browsercode](https://github.com/leaningtech/browsercode); [Sacra](https://sacra.com/chat/h/d55eb00f-fe8d-43fb-8e03-e767c6619a2f/)
- BrowserPod's paid "Edge" add-on provides public web links to services running inside a browser pod — i.e. a tab acting as a host reachable by others, via the vendor's relay. *(snippet)* — [BusinessCloud](https://businesscloud.co.uk/?p=273913)
- A vendor blog (Blaxel) argues the client-side model differs from cloud agent workloads that need persistent state and hardware isolation — i.e. browser sandboxes die with the tab and are weaker for long-running agents. *(snippet, vendor-biased)* — [Blaxel](https://blaxel.ai/blog/browser-sandboxing-for-coding-agents)

### Inferences
- The "user-owned compute" options that a static page could plausibly attach to with only OAuth/token and no install: (a) GitHub Codespaces via the user's GitHub token (REST API to create/start a codespace, then reach a forwarded port) — the free quota is real, but CORS and port-forwarding auth from a third-party origin are unverified; (b) Cloudflare Sandbox in the user's own account — needs the $5 paid plan, so not free; (c) E2B/Daytona/Modal with the user's own API key — free credits exist but browser-direct API access (CORS) is unverified.
- The peer-to-peer design maps cleanly onto the `Sandbox` interface seam from §2: a desktop member's tab runs a tier-3 engine (or a native helper) and exposes bash/readFile/writeFile over a WebRTC data channel (signalled over the existing Nostr room); mobile members' agents use the remote implementation. Trust becomes explicit: the host sees plaintext commands/files, and guests' agents can run code in the host's tab sandbox — so the host needs an egress allowlist and resource caps.
- Tab lifetime is the main operational weakness of any in-browser host (background-tab throttling, BrowserPod's 10-hour cap, mobile OS killing PWAs), so agents must be designed as resumable from room state rather than long-lived processes.

### Gaps
- Not verified: Codespaces REST API usability from a browser origin (CORS, scopes, whether OAuth Apps can create codespaces), Cloudflare "user's own account" deploy flows, Google Colab / Firebase Studio / HF Spaces / Deno Deploy / val.town as attachable compute, GitHub Actions as an on-demand runner (workflow_dispatch) — no sources gathered.
- Found no prior art for P2P/volunteer sandbox sharing over WebRTC among chat members; absence of results is from limited searching, not proof of absence.
- **Unverified background (leads):** Google Colab's ToS restricts non-interactive/remote-control use on free tier; HF Spaces free CPU tier (2 vCPU/16 GB) sleeps after inactivity and can be duplicated into a user's account with a token; val.town and Deno Deploy let a user host a tiny HTTP relay/CORS proxy for free under their own account — the lightest "user-owned backend" for CORS-proxy and MCP-relay needs; GitHub's REST API is CORS-enabled for token-authenticated requests.

## 6. Known security incidents and lessons for in-browser / sandboxed agents

### Takeaway
The recurring failure is not sandbox escape but data exfiltration by prompt injection through any allowed outbound channel — rendered markdown images/links, allow-listed vendor APIs, DNS, or pre-approved "safe" commands. For a browser-hosted agent the controlling levers are a tight CSP `connect-src`, never auto-rendering model-produced URLs, isolating untrusted output in sandboxed iframes on a different origin, and keeping secrets (API keys, room keys, OAuth tokens) outside the context where model-written code runs.

### Cited Findings
- Markdown-image exfiltration still works across products in 2026; recommended fix is never letting the browser fetch model-output image URLs directly. The chat UI is the "external communication" leg of the lethal trifecta (private data + untrusted content + outbound channel). *(snippet)* — [Archestra](https://archestra.ai/blog/data-exfiltration-via-markdown-image); [Simon Willison's exfiltration-attacks tag](https://simonwillison.net/tags/exfiltration-attacks)
- "ChatGPhish" (May 2026): the chatgpt.com response renderer trusted Markdown links and image URLs from pages the assistant had summarised. *(snippet)* — [The Hacker News](https://thehackernews.com/2026/05/chatgphish-vulnerability-turns-chatgpt.html)
- "Claudy Day" (Oasis Security, Mar 2026): chained hidden instructions in pre-filled chat URLs (`?q=`), exfiltration through Anthropic's Files API, and an open redirect on claude.com; needed no integrations, tools or MCP servers. Anthropic fixed the injection and was mitigating the rest. *(snippet)* — [Oasis Security](https://oasis.security/blog/claude-ai-prompt-injection-data-exfiltration-vulnerability)
- "Claude Pirate" (Embrace The Red, Oct 2025): Claude's code-execution sandbox had network egress allow-listed to Anthropic's API; an injected prompt made it upload user data to the *attacker's* Anthropic account via the Files API — an allow-listed domain is itself an exfiltration channel when the attacker can hold an account there. *(snippet)* — [Embrace The Red](https://embracethered.com/blog/posts/2025/claude-abusing-network-access-and-anthropic-api-for-data-exfiltration); [The Register](https://www.theregister.com/2025/10/30/anthropics_claude_private_data/)
- Claude Code CVE-2025-55284: indirect prompt injection exfiltrated data (e.g. API keys) via DNS requests using commands on the no-approval allow-list. *(snippet)* — [Embrace The Red](https://embracethered.com/blog/posts/2025/claude-code-exfiltration-via-dns-requests)
- Web/browser agents: hidden payloads in page HTML comments instruct the agent to put environment variables into a markdown image URL. *(snippet)* — [Promptfoo](https://www.promptfoo.dev/blog/indirect-prompt-injection-web-agents/)
- Google classed browser-agent data exfiltration in Antigravity as a known issue / intended behaviour, ineligible for bounty (per Simon Willison's summary). *(snippet)* — [Simon Willison, Johann Rehberger tag](https://simonwillison.net/tags/johann-rehberger/)
- A Claude Chrome-extension flaw allowed a visited page to take over the agent with no clicks (reported by TechRadar/Dark Reading) — extension-based agents inherit the user's full browser authority. *(snippet)* — [TechRadar](https://www.techradar.com/pro/security/no-clicks-no-permission-prompts-just-visit-a-page-and-an-attacker-completely-controls-your-browser-experts-warn-claude-chrome-extension-could-let-hackers-hijack-your-online-browsing); [Dark Reading](https://darkreading.com/vulnerabilities-threats/claude-flaw-malicious-prompts-ai-agents)
- Co-do's author lists residual browser-sandbox doubts: uncertain whether CSP blocks Beacon and DNS-prefetch paths; iframe `csp` attribute is Blink-only; provider-side tools (web search) add exfiltration paths; generated files can be dangerous outside the browser; permission fatigue. *(fetched)* — [aifoc.us](https://aifoc.us/the-browser-is-the-sandbox/)
- BrowserCode restricts pod egress to an allowlist (npm, Yarn, GitHub, AI provider APIs). *(fetched)* — [leaningtech/browsercode](https://github.com/leaningtech/browsercode)
- NVIDIA published guidance on sandboxing agentic workflows with WebAssembly (in-browser Pyodide execution of LLM-generated code to shift risk off the server). *(snippet)* — [NVIDIA developer blog](https://developer.nvidia.com/blog/sandboxing-agentic-ai-workflows-with-webassembly/)

### Inferences
- Beamhop-specific: a group chat is a multi-party prompt-injection surface by construction — every other member's message, shared file, skill, and any web/MCP content is untrusted input to *my* agent, which holds *my* API key and can read the decrypted room. "Claude Pirate" generalises directly: allowing `connect-src api.anthropic.com` is enough for exfiltration to an attacker-owned account, and allow-listing npm/GitHub (as BrowserCode does) allows exfiltration by publishing/pushing. An egress allowlist alone is not a defence when the agent can run code.
- Practical mitigations implied by the incidents: (1) the code-execution sandbox (iframe/Worker) gets `connect-src 'none'` and no access to keys — only the trusted harness origin talks to the LLM/MCP; (2) do not render model-emitted remote images/links without a click-through; (3) no "auto-approved" commands that can reach the network (DNS/`fetch` equivalents); (4) treat agent output posted back into the room as untrusted for *other* members' agents (agent-to-agent injection chains); (5) per-room, per-agent capability grants shown to all members.
- An in-tab agent on the app's own origin has more at stake than a server sandbox: same-origin code can read IndexedDB (Nostr private keys, room keys). Running model-written code on a *separate origin* (sandboxed iframe without `allow-same-origin`, as Co-do and pi-web-ui do) is mandatory, not optional. On GitHub Pages, per-user/per-project subpaths share an origin with other paths on the same host — a custom domain or dedicated sandbox origin matters.

### Gaps
- Found no documented sandbox *escape* from WebContainers, BrowserPod, Claude artifacts' iframe, or ChatGPT canvas; searches surfaced only exfiltration-class issues. This is absence of results from a single search, not evidence of none.
- No incident reports specific to multi-user/group-chat agents were found.
- Details of Claude artifacts' sandbox/CSP configuration and storage limits were not retrieved.
